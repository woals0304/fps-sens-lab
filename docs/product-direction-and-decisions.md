# FPS 감도 진단기 제품 방향과 의사결정

- 작성일: 2026-07-26
- 문서 상태: 현재 제품 방향의 기준 문서
- 적용 범위: 사용자 경험, 시험 설계, 오버워치 연계, 데이터 수집, AI·PyTorch 활용

## 한 문장 정의

사용자를 오래 붙잡거나 과장된 약속을 하지 않으면서, 짧은 조준 시험만으로 바로 적용해 볼 만한 감도와 안정 범위를 제시하는 오버워치 중심의 실용 도구다.

이 프로젝트는 AI 기술을 보여 주는 데 목적이 있지 않다. 사용자가 느껴야 할 핵심 가치는 다음과 같다.

> 귀찮지 않은데 생각보다 꼼꼼하고, 짧게 해봤는데 바로 써먹을 수 있다.

## 제품 목적

### 해결하려는 문제

- 사용자가 감도를 바꿔 보면서도 어느 방향이 나은지 판단하기 어렵다.
- 기존 감도 추천은 유명 선수 설정, 단일 환산값 또는 긴 반복 훈련에 치우치기 쉽다.
- 감도를 찾는 과정 자체가 길고 반복적이면 결과를 받기 전에 이탈한다.
- 지나치게 정밀한 숫자나 AI 신뢰도를 내세우면 실제 근거보다 강한 확신을 줄 수 있다.

### 제공해야 하는 가치

- DPI와 현재 감도만으로 빠르게 시작한다.
- 플릭, 추적, 회전 반응에서 나타나는 차이를 함께 측정한다.
- 최종 결과로 추천 감도, 안정 범위와 이해하기 쉬운 이유를 제시한다.
- 결과가 충분히 뚜렷하면 시험을 일찍 끝낸다.
- 애매한 경우에만 짧은 비교를 한 번 더 진행한다.
- 오버워치에 직접 적용하거나 선택적 실제 게임 검증으로 자연스럽게 이어진다.

## 최상위 제품 원칙

### 1. 짧은 완료가 미세한 정확도보다 우선이다

- 기본 흐름은 2~5분 안에 끝나야 하며, 체감 시간은 그보다 짧아야 한다.
- 첫 유용한 판단은 가능한 한 이른 시점에 제공한다.
- 후보 수를 고정해서 모두 시험하지 않고, 결과가 분명하면 조기 종료한다.
- 반복되는 과제는 길게 늘리지 않고 짧은 묶음으로 구성한다.
- 예상 남은 시간과 진행 상태는 명확하게 보여 준다.

90초 안팎의 핵심 진단은 유력한 목표이지만, 아직 실제 사용자 측정으로 확정된 기준은 아니다. 완료 시간뿐 아니라 중도 이탈률과 결과 일관성을 함께 확인해 결정한다.

### 2. 사용자에게 숙제나 일정을 요구하지 않는다

- 며칠 뒤 다시 오라는 일정은 기본 결과의 전제 조건이 아니다.
- 7일 루틴, 반복 검사, 장기 기록은 있어도 완전히 선택적인 후속 기능이어야 한다.
- 사용자가 당장 원하는 것은 훈련 계획보다 지금 적용할 감도 판단이다.
- 추가 검사가 필요하면 이유와 예상 시간을 먼저 알려 주고 한 번의 짧은 선택으로 끝낸다.

### 3. 확인할 수 없는 효과를 약속하지 않는다

- 감도를 바꾼 뒤 승률이나 전적이 좋아졌다고 자동으로 단정하지 않는다.
- 감도 변경 시점과 경기 데이터가 모두 있어도 영웅, 맵, 팀, 패치, 컨디션 등의 영향이 섞이므로 인과관계로 표현하지 않는다.
- 공식 경기 데이터가 없다면 브라우저 시험 결과와 사용자가 직접 제공한 정보만 사용한다.
- 결과는 `최적 감도 확정`보다 `현재 측정에서 가장 안정적인 후보`처럼 근거 수준에 맞게 표현한다.

### 4. AI가 아니라 결과가 보이게 한다

- 사용자 화면에서 `AI 추천`, `딥러닝 분석` 같은 표현을 핵심 가치로 내세우지 않는다.
- 기술 명칭 대신 `추천 확신도`, `추가 비교 필요 여부`, `결과가 충분히 뚜렷함`처럼 사용자가 이해할 결과를 보여 준다.
- 긴 생성형 문장, 과도한 카드, 비슷한 설명의 반복을 피한다.
- 화면은 화려한 데모보다 사람이 목적에 맞게 다듬은 도구처럼 간결해야 한다.
- 상세 수치와 연구 근거는 기본 흐름을 방해하지 않는 `자세히 보기`에 둔다.

### 5. 재미는 장식보다 피드백에서 만든다

- 한 과제가 끝날 때마다 짧고 명확한 반응을 준다.
- 다음 단계가 왜 선택됐는지를 한 문장 이내로 알려 준다.
- 결과가 좁혀지는 느낌을 진행 과정에서 체감하게 한다.
- 게임을 흉내 낸 장식보다 조작 반응, 표적 피드백과 매끄러운 전환을 우선한다.

## 기본 사용자 흐름

1. 사용자가 DPI와 현재 오버워치 감도를 입력한다.
2. 별도의 복잡한 설정 없이 빠른 시험을 시작한다.
3. 플릭, 추적, 회전 과제를 짧게 수행한다.
4. 측정 결과가 분명하면 즉시 종료한다.
5. 애매한 구간만 A/B 방식으로 한 번 더 비교한다.
6. 추천 감도, 안정 범위와 핵심 이유를 바로 보여 준다.
7. 세부 지표, 연구 설명, 실제 오버워치 검증은 원하는 사용자만 연다.

기본 흐름에서 요구하지 않을 항목:

- 최소·최대 감도 직접 설정
- 시험 간격 직접 설정
- 일정 또는 재방문 날짜
- 계정 로그인
- 이메일 입력
- AI 예측 파일 가져오기
- 장문의 사전 설문

## 오버워치 체감 일치 기준

### 화면과 카메라

- FPS 시험의 1차 검증 화면 비율은 오버워치의 일반적인 16:9 환경으로 둔다.
- 기준 시야각은 오버워치 가로 FOV 103을 사용한다.
- 렌더러에는 실제 캔버스 비율에 맞게 계산한 세로 FOV를 전달한다.
- 16:9가 아닌 창에서는 시험 화면을 중앙 레터박스로 맞춰 투영 비율을 유지한다. 화면의 물리적 크기까지 실제 게임과 같다고 과장하지 않는다.
- 데스크톱 1920×1080, 1600×900 또는 1280×720 중 하나 이상에서 실제 시험 흐름을 점검한다.

### 회전과 입력

- 오버워치 yaw 기준값 `0.0066`을 사용해 회전 거리와 `cm/360`을 계산한다.
- 원시 입력 사용 여부를 감지하고 일반 포인터 잠금으로 전환된 경우 이를 측정 품질 정보로 남긴다.
- 포인터 잠금 해제, 창 포커스 손실, 심한 프레임 지연이 발생하면 해당 구간의 기록을 신뢰하지 않는다.
- 웹 환경과 게임 엔진의 체감이 완전히 동일하다고 표현하지 않고, 회전 거리와 시야각을 맞춘 근사 환경이라고 설명한다.

## 오버워치 연동 방향

### 공개 API

2026-07-26 조사 기준, 공식적으로 공개된 오버워치 2 경기 전적·감도 설정·리플레이 원시 데이터 API는 확인되지 않았다. Battle.net OAuth가 있더라도 감도나 조준 데이터를 제공하는 것은 아니다.

- [Battle.net 개발자 문서](https://community.developer.battle.net/documentation)
- [오버워치 2 API 요청 논의](https://us.forums.blizzard.com/en/blizzard/t/overwatch-2-api/19214)

따라서 제품 핵심 기능을 비공식 전적 사이트나 존재 여부가 불확실한 API에 의존시키지 않는다.

### 가장 현실적인 실제 게임 검증

선택적인 오버워치 Workshop 검증이 가장 현실적인 방향이다.

1. 웹에서 감도 후보를 빠르게 찾는다.
2. 사용자가 추천 감도를 오버워치에 직접 적용한다.
3. 무료 Workshop에서 30~45초 정도 짧게 검증한다.
4. Workshop HUD에 간단한 결과 코드나 수치를 표시한다.
5. 사용자가 결과를 웹에 직접 입력해 최종 판단에 보탠다.

Workshop은 실제 게임 안의 조준 방향, 위치, 피해 이벤트와 시간을 활용할 수 있지만 마우스 원시 입력, 사용자 감도 설정 변경, 외부 서버 전송 수단으로 간주해서는 안 된다.

결과 코드는 버전, 표적 획득 시간, 적중률과 추적 유지율처럼 사용자가 확인할 수 있는 최소 수치만 담는다. 리플레이 공유 코드는 분석 API가 아니며 패치 뒤 만료될 수 있으므로 자동 데이터 연동 수단으로 사용하지 않는다.

- [오버워치 Workshop 공식 소개](https://overwatch.blizzard.com/ko-kr/news/22938941/introducing-the-overwatch-workshop/)
- [오버워치 리플레이 공식 소개](https://overwatch.blizzard.com/en-us/news/23000187/)

### 지켜야 할 안전선

허용 가능한 방향:

- 브라우저 안에서 독립적으로 수행하는 시험
- Workshop 내부 측정과 HUD 결과 표시
- 사용자가 결과 코드나 수치를 직접 옮기는 방식
- 사용자가 명시적으로 내보낸 세션 데이터 분석

피할 방향:

- 게임 메모리 읽기
- DLL 주입, 프로세스 후킹 또는 패킷 감청
- 매크로를 이용한 조준·발사·설정 자동 변경
- 비공개 리플레이 파일이나 캐시 역분석
- 게임 중 경쟁 정보를 읽어 주는 실시간 오버레이

## 측정과 데이터 원칙

### 현재 활용 가치가 높은 지표

- 플릭: 명중률, 한 번에 맞춘 비율, 목표 도달 시간, 보정 시간, 오버슈트와 재진입
- 추적: 평균 각도 오차, 표적 위 체류율, 안정성, 부드러움, 추적 손실과 보정 빈도
- 회전: 완료 시간, 각도 오차, 오버슈트, 보정 횟수와 안정화 시간

### 추가로 기록해야 할 측정 품질 정보

- 시험 규약 버전
- 원시 입력 사용 여부
- 포인터 잠금 중단 여부
- 프레임 시간 또는 긴 프레임 발생 비율
- 화면 크기와 실제 렌더링 비율
- 적용 FOV와 회전 보정값
- 후보 및 과제 제시 순서
- 장치 설정이 달라졌는지 확인할 수 있는 최소 정보

### 데이터 수집 원칙

- 기본값은 로컬 저장이다.
- 서버 수집은 명확한 동의와 목적 설명이 있을 때만 추가한다.
- 장기 일정을 요구하지 않고 기존 시험 과정에서 생긴 데이터만 활용한다.
- 학습용 데이터는 익명화하고 삭제 또는 내보내기 선택권을 제공한다.
- 모델 학습·검증·시험 데이터는 시행 단위가 아니라 사용자 단위로 분리한다.

## PyTorch와 AI 활용 결정

### 현재 구현에 대한 판단

현재 `ai/` 모듈은 실사용 기능이 아니라 기술 검토용 뼈대에 가깝다.

- 작은 MLP가 특징값에서 최적 감도를 직접 회귀한다.
- 특징 스키마, 정규화, 학습·검증 분리와 품질 평가가 정의되지 않았다.
- 예측 신뢰도는 실제 계산값이 아니라 고정값이다.
- 결과 JSON을 사용자가 직접 불러오는 흐름은 일반 사용자 경험에 맞지 않는다.
- 빠른 시험에서 모을 수 있는 기록 수와 AI 기능의 준비 조건이 맞지 않는다.

따라서 현재 모델의 출력을 제품 추천 근거로 사용하지 않는다.

### 가장 적합한 PyTorch 역할

감도를 소수점 숫자로 직접 예측하는 회귀 모델보다 후보 간 비교 모델이 적합하다.

입력 예시:

- 후보 A와 B의 감도 차이
- 두 후보의 플릭·추적·회전 지표 차이
- DPI, 현재 감도와 `cm/360`
- 시험 규약과 제시 순서
- 원시 입력과 프레임 품질 정보

출력 예시:

- A가 더 나을 확률
- 두 후보가 사실상 비슷할 확률
- B가 더 나을 확률
- 추가 비교가 필요한지 여부

이 모델의 목적은 정답처럼 보이는 숫자를 만드는 것이 아니라 다음 두 가지다.

1. 결과가 분명할 때 시험을 더 빨리 끝낸다.
2. 애매할 때 가장 정보가 많은 후보 한 쌍만 추가한다.

### 도입 순서

1. 규칙 기반 추천과 조기 종료를 기준선으로 유지한다.
2. QUEST+, Bradley–Terry 또는 Bayesian 방식으로 적응형 후보 선택을 먼저 검증한다.
3. 기존 점수에서 다시 만든 가짜 라벨이 아닌 독립적인 최종 검증 결과를 모은다.
4. 충분한 사용자 데이터가 쌓인 뒤 PyTorch pairwise 모델을 학습한다.
5. 모델은 추천에 개입하지 않는 shadow mode에서 기존 로직과 비교한다.
6. 사용자 단위 미사용 데이터에서 정확도, 검사 횟수와 확률 보정을 검증한다.
7. 동일하거나 더 나은 결과를 더 적은 시험으로 낼 때만 실제 흐름에 반영한다.

학습은 PyTorch로 하고, 검증된 작은 모델은 ONNX로 내보내 브라우저에서 로컬 실행할 수 있다.

- [PyTorch ONNX 공식 문서](https://docs.pytorch.org/docs/stable/onnx.html)

### 당장 하지 않을 AI 기능

- 한 번의 짧은 세션만으로 정확한 개인 최적 감도 회귀
- 고정값 또는 근거 없는 신뢰도 표시
- 전적이나 승률 향상을 예측하는 모델
- 원시 궤적 데이터 없이 만드는 CNN·RNN 모델
- 사용자 화면에서 AI 기능을 별도 상품처럼 강조하는 구성

## 성공 판단 기준

제품이 성공했다고 보려면 단순히 추천 숫자가 출력되는 것만으로는 부족하다.

- 대부분의 사용자가 기본 흐름을 중도 이탈 없이 완료한다.
- 같은 조건으로 다시 검사했을 때 추천 감도 또는 안정 범위가 크게 흔들리지 않는다.
- 전체 후보를 시험하지 않아도 긴 규약과 비교해 비슷한 결론에 도달한다.
- 사용자는 결과를 이해하고 바로 오버워치에 적용할 수 있다.
- 추천이 애매한 경우 시스템도 애매하다고 말할 수 있다.
- AI 도입 후에도 정확도뿐 아니라 중앙 시험 횟수와 체감 시간이 실제로 줄어든다.

## 최종 의사결정 요약

- 핵심 제품은 짧고 실용적인 감도 진단이며 AI 데모가 아니다.
- 사용자에게 일정, 장기 기록 또는 반복 방문을 요구하지 않는다.
- 전적 향상이나 인과관계를 확인할 수 있는 것처럼 표현하지 않는다.
- 오버워치 16:9, FOV 103과 yaw `0.0066`을 1차 검증 기준으로 삼는다.
- 공개 오버워치 API에 의존하지 않는다.
- 실제 게임 검증은 선택적인 Workshop 방식이 가장 현실적이다.
- PyTorch의 최우선 역할은 직접 감도 회귀가 아니라 A/B 순위와 조기 종료다.
- PyTorch 도입 전에는 적응형 통계 방식과 데이터 품질 체계를 먼저 완성한다.
- 사용자 화면에서는 AI보다 결과의 명확성, 속도와 신뢰도를 보여 준다.

## 2026-07-26 P0 반영 기록

- 오버워치와 같은 16:9 화면 비율에서 홈과 결과 화면을 직접 점검했다.
- 결과 직후 노출되던 7일 훈련 리포트·이메일 관심 등록 카드를 기본 흐름에서 제거했다.
- 개발용 AI 예측 파일 불러오기와 외부 예측 패널을 사용자 화면에서 제거했다. 기존 저장 필드와 파서는 호환성을 위해 유지한다.
- 추천 안정 범위가 확정되지 않았는데 별도 분석 문장이 안정 구간을 단정하던 불일치를 수정했다.
- 결과 첫 화면은 현재 감도 대비 변화량과 최종 확인 결과만 짧게 설명하도록 정리했다.
- 상세 결과의 중복 해석 카드를 줄이고 점수, 후보, 검증과 원기록은 탭에서 계속 확인할 수 있게 유지했다.
- 유지·변경 기준 사이의 애매한 검증 결과는 통과로 확정하지 않고 `판단 보류`로 남긴다.
- 무명중 플릭의 빈 시간값을 빠른 반응으로 보상하지 않도록 0점 처리와 회귀 테스트를 추가했다.
- 빠른 진단의 측정 상한 도달을 높은 확신에 따른 조기 종료처럼 표현하지 않도록 종료 사유를 분리했다.
- 포인터 잠금 요청은 실제 성공 이벤트를 확인한 뒤에만 측정을 시작하며, 비동기 실패와 무응답은 같은 과제 재시작으로 복구한다.
- 완료한 과제는 예상 시간에서 즉시 제외하고, 빠른 모드에만 시간 상한을 적용하며, 예정 비교 수와 ETA가 최종 확인까지 같은 범위를 가리키도록 맞췄다.
- 몰입형 시험과 고급 실험실 캔버스를 16:9로 고정했다. 1600×900에서는 캔버스가 화면 전체와 정확히 일치했고, 1440×1000에서는 1440×810 중앙 레터박스로 유지되는 것을 앱 내 브라우저에서 확인했다.
- Raw Input 사용 여부, 50ms 이상 프레임 비율, 최대 프레임 공백, 실제 캔버스 크기·비율, 수평·수직 FOV와 회전 보정값을 버전형 품질 스냅샷으로 실행 기록에 저장한다.
- 250ms 이상 프레임 공백은 렌더 프레임뿐 아니라 클릭·마우스 이동 직전에도 확인해 현재 과제를 저장하지 않고 처음부터 다시 시작한다. 포인터 잠금, 창 포커스와 화면 가림 중단도 같은 원칙으로 한 번만 무효화한다.
- 품질 필드는 기존 저장 기록에 없어도 정상으로 취급하고, 손상된 품질 필드만 마이그레이션에서 버려 기존 실행과 추천 계산은 보존한다.
- 자동 과제 사이에 800ms 전환 안내를 넣고, 실행 중 HUD는 현재 행동과 진행률만 한 줄로 보여 준다.
- 후보 순서는 현재 감도에서 시작해 낮은 값과 높은 값을 번갈아 확인하는 재현 가능한 중심 우선 순서로 바꿨다.
- 빠른 진단의 조기 종료는 플릭·추적·회전 한 묶음이 끝난 시점에만 판단하며, 양쪽 후보가 없거나 최고점이 탐색 가장자리이거나 과속·저속 경향이면 측정을 계속한다.
- 고급 실험실의 입력 보정 배율은 첫 실행 뒤 잠가 후보별 비교 조건이 섞이지 않게 했다.
- 측정 완료 직후에는 로컬 실행 상태도 즉시 닫고, 브라우저 저장 실패가 확인되면 다음 과제로 넘어가지 않은 채 같은 작업 재시작 안내를 보여 준다.
- 최종 자동 검증은 31개 테스트 파일의 115개 테스트와 프로덕션 빌드를 통과했다. Three.js 실행 묶음의 500kB 초과 경고는 후속 성능 최적화 항목으로 남긴다.
